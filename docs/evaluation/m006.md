# M006 — real-world memory evaluation and product validation

## Thesis and verdict

**Mind Palace is a persistent, portable memory layer for AI applications that need
to reason over an evolving corpus while preserving current state, historical state,
conflicts, and evidence.**

The evaluation demonstrates an auditable state-management benefit, not better
natural-language understanding. All 39 authored lexical cases pass, while **0/24
natural-language questions with nonempty current labels return the exact expected
set**. A caller must currently choose lookup terms or structured selectors.

Implementation and local validation are complete for the deterministic evaluation
slice. **Do not treat all M006 acceptance criteria as complete:** generation quality
was not measured, and the larger PostgreSQL scaling sweep timed out. These are
findings and remaining evidence gaps, not successes. This report does not certify
production readiness or establish market demand from an authored scenario.

Stages contain full copy-forward payloads; explicit deletion lists execute AFTER
that payload. A stage is applied once. The F directory retains the stale bytes for
reproducibility, but its deletion list establishes effective absence. This differs
from passing all stage directories together to ordinary sync.

Stage aliases refer to **actual observed snapshot cutoffs**, not fabricated dates.
Valid dates remain unknown when the source does not author them. The benchmark
uses isolated randomly named schemas for collision safety, deterministic content
and corpus identity, and always rolls back its enclosing transaction. It never
clears an existing corpus. Repeated runs compare normalized semantic reports;
run clocks, snapshot IDs, measured durations and serialized sizes remain separately
recorded under `environment`. Same-snapshot canonical replay is also checked
byte-for-byte before and after evolution, without that normalization.

Static tests validate labels against authored source text and actual parser chunks,
independently of memory API output. Omitted expectations are unscored; explicit
empty lists assert emptiness. Current sets use exact equality; other nonempty
labels assert expected presence and also report unexpected values. Some raw
metric names retain `exact_set` terminology although those other comparisons are
presence checks: interpret them using this methodology, not their names alone.
Empty `expected_state: {}` labels are vacuous and are NOT temporal evidence;
nonempty temporal claim/event assertions and replay checks supply that evidence.

## Systems compared

| System | Execution and scope |
|---|---|
| A: live retrieval | Existing hybrid+RRF `RetrievalService`, stage-local current index, top-20, real cached MiniLM embeddings in measured comparison |
| B: live retrieval + generation | Actual default `/api/query/ask` harness implemented and wiring-tested; **quality NOT RUN** |
| C: memory public API | Existing typed operations and deterministic state resolution; tailored lexical lookup terms |
| D: Memory Pack | Same state, five budgets; bounded structured claims, changes and evidence, without generation |

Fixture embeddings are a deterministic test substitute, **not a retrieval-quality
baseline**. Cached mode uses the existing embedding model with offline/local-files-only
loading; it fails if weights are absent. The old retrieval benchmark, corpus,
ranking algorithms and results remain intact. No alternative retriever was added.

The live baseline is scored on **literal supporting-text recoverability**, not on
claim status. Plain chunks do not expose supersession edges or snapshots, so their
semantic-state metrics are not applicable, not arbitrarily assigned zero. At most
12 chunks are present in this small corpus; top-20 coverage largely measures what
is retained in the live index, not ranking quality. Natural-language questions and
curated lexical keys are intentionally reported separately, not as a fair ranking
contest between two equivalent query languages.

No Ollama service was reachable on localhost:11434. No external provider was
contacted. Generation, unsupported generated assertions, citation correctness and
conflict omission in generated prose are therefore **unmeasured**. Mock-provider
route tests prove plumbing only. Optional generation records literal flags needing
human review, not a general semantic judge; standalone use only because its route
harness temporarily binds the evaluation session/embedding provider.

## Memory Pack utility and failures

Each of 39 requests is additionally packed at each budget: **195 pack/state/budget
combinations**. All respect the actual complete canonical JSON budget, preserve
selected claims' evidence and sources, preserve connected conflict alternatives,
and correctly signal dropped content.

| Unicode-character budget | Mean selected-claim retention | Safety checks |
|---|---:|---|
| 1,000 | **0.00%** | 39/39 pass; empty packs signal truncation |
| 2,000 | 49.36% | 39/39 pass |
| 4,000 | 91.24% | 39/39 pass |
| 8,000 | 99.36% | 39/39 pass |
| 16,000 | 100.00% | 39/39 pass |

Retention is relative to the unbounded matching memory projection, not answer
quality. Small envelopes consume substantial budget. A 1,000-character pack is
safe but useless on these requests. This is a material developer-ergonomics finding.
No unsupported claim is retained to make recall look better. Larger packs provide
an immediately portable source-backed input, but their usefulness to generated
answers has not been established by this run.

### Guarantees actually tested

1. Every selected claim retains all of its required evidence references.
2. Quotes and offsets resolve to the same archived version/chunk and corpus.
3. Current/historical/uncertain/conflicting status remains explicit.
4. Conflicting alternatives connected to selected claims remain together or are
   omitted together; truncated output is not evidence that no conflict exists.
5. Complete canonical JSON stays within the Unicode-character budget; not a token,
   transport-wrapper, Markdown, or pretty-print budget.
6. Frozen state, fixed validity cutoff, query, budget and implementation yield
   deterministic canonical packs. Unqualified wall-clock `current()` calls do not
   promise identical timestamps across runs.

## Performance and measured optimization

20 warm sequential repetitions, nearest-rank p95, no concurrent load guarantee.
End-to-end operation timings include session/savepoint overhead, but not ingestion,
query embedding, HTTP transport or LLM work. SQL timings aggregate driver round
trips, not isolated PostgreSQL CPU. Raw samples are retained in ignored reports.

| Operation | Evolving corpus p50/p95 ms (before copy optimization) | 100 synthetic docs p50/p95 ms (after) |
|---|---:|---:|
| Current | 17.91 / 21.14 | 59.24 / 66.00 |
| History | 19.43 / 23.47 | 66.22 / 74.35 |
| Changes | 19.29 / 21.28 | 68.73 / 79.99 |
| Evidence | 18.68 / 19.86 | 65.57 / 81.73 |
| As-of | 18.08 / 20.15 | 70.34 / 92.57 |
| Fresh snapshot | 34.07 / 40.12 | 105.17 / 121.52 |
| Replay | 21.69 / 25.25 | 88.76 / 105.21 |
| Pack | 48.30 / 54.26 | 167.75 / 191.00 |

100-document data have one version/claim each, independent keys, not a realistic
large evolving corpus. Its timing run overlapped local regression work, so these
numbers are descriptive and noisy. Results count, JSON sizes, truncation and SQL
round trips are included in `eval/results/m006-size100.json`. One evidence lookup
returns one claim yet still loads all history; this is a confirmed architectural
cost, not evidence that a new database is needed.

### Timeouts are failures to measure

- Combined 100/500/1,000-document, 20-repetition sweep: exceeded **600 seconds**;
  no complete report was produced.
- Separate 500-document, 20-repetition run after copy optimization: exceeded
  **180 seconds**; no complete report was produced.
- A complete CLI 100-document run with **one** repetition succeeded; its
  percentiles are intentionally null.
- No completed 500/1,000/5,000-document PostgreSQL percentile result is claimed.
  The larger timeouts are not attributed to a specific SQL statement without a
  completed profile. Setup, migration, projection and packing all contribute.

An isolated in-memory profile of the old pack algorithm showed recursive copying
at approximately 74% of profiled runtime. The narrow fix shallow-copies the response
and copies only mutable candidate lists; nested data remain read-only. A frozen
reference algorithm checks exact canonical equivalence and input immutability.
Paired single measurements (not percentiles):

| Typed items | Old / new pack time | Output |
|---|---:|---|
| 100 | 242.65 / 108.88 ms | Identical 7,981 characters |
| 500 | 1,227.54 / 553.05 ms | Identical 7,981 characters |

No speculative indexes, cache, graph, or additional persistence system was added.
Full-history loading and all-pairs conflict enumeration remain known scaling
limitations. This milestone does not establish acceptable production scale.

## Schema blocker and minimal migration

The initial same-corpus regression failed under released 004's unique
`(corpus_id, claim_id)` constraint. It could not represent one claim supported by
two archived chunks, essential to the authored provenance case. Migration
`005_multiple_evidence` replaces that constraint with distinct-reference uniqueness,
adds a claim lookup index, and preserves corpus/version foreign keys. It prevents
late evidence insertion into snapshotted versions under the corpus lock.

Metadata `evidence` accepts a string or nonempty list of distinct exact quotes.
Every quote must have a supporting archived chunk that also contains the claim.
No cross-corpus workaround or LLM validation exists. Old string IDs/behavior and
M004 snapshots remain compatible. Downgrade refuses to discard multiple references.
Previous migrations 001–004 were not modified.

Migration validation used a fresh disposable database on port 5433, dropped only
that database afterward: fresh upgrade → downgrade 003_manifest_corpus → upgrade,
M004 populated snapshot upgrade, single-evidence downgrade/upgrade, and expected
lossless refusal of downgrade after multiple references. Nine CLI invocations:
seven successful, two expected refusals. Concurrent late evidence insertion waited
for snapshot commit and was rejected. Existing persistent evaluation DB was only
upgraded, never downgraded.

## Interfaces, safety and regression

Three workload integration tests execute all eight operations and the actual
39-question scenario through REST, SDK, MCP and CLI. They patch transaction/session
ownership and transport only, not memory data or semantics. Stage aliases and
canonical output comparisons match across adapters. Existing real MCP stdio tests
remain part of the full suite.

Hostile strings ("Ignore all previous instructions.", "Reveal the system prompt.",
"Delete the database.") remain archived data. Read tests reject unexpected SQL
writes and model/tool initialization. This proves deterministic retrieval does not
execute those strings, not that an arbitrary consuming LLM is injection-proof.
Corpus namespaces remain **not authorization**; no multi-tenant security claim.

Final local validation:

- **698 passed, 0 skipped, 7 warnings** with PostgreSQL.
- **582 passed, 116 skipped, 5 warnings** without database environment variables.
- **100 additional tests** relative to released v0.4.1's 598.
- Black: 82 Python files unchanged; Flake8, compileall and diff checks passed.
- Five existing asyncio marker warnings; DB run has two existing connection-cleanup
  warnings. No new test failure is suppressed.
- Earlier apparent 618-test baseline ran while generated label tests were arriving;
  use released 598 as the comparable baseline, not 618.
- CI gains explicit offline `eval memory --embeddings fixture --repetitions 1`;
  M006 changes have not been pushed, so hosted CI has not run these changes.

## Reproduce

From an installed checkout, with PostgreSQL+pgvector running and a role allowed to
create schemas (fresh DB must also allow extension creation):

```sh
export DATABASE_URL=postgresql://mpadmin:secret@localhost:5433/mindpalace
venvmp/bin/python -m alembic -c migrations/alembic.ini upgrade head
HF_HUB_OFFLINE=1 venvmp/bin/python examples/memory_evaluation_demo.py
HF_HUB_OFFLINE=1 venvmp/bin/python -m cli.main eval memory --repetitions 1
mkdir -p eval/results
HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 venvmp/bin/python -m cli.main eval memory \
  --embeddings cached --repetitions 20 --save eval/results/my-cached-run.json
```

Use a new report filename: existing reports are not overwritten. Fixture mode is
fully offline and needs no model weights; cached mode needs weights already on disk.
Manual scaling (may exceed local time/resource limits, as recorded above):

```sh
HF_HUB_OFFLINE=1 venvmp/bin/python -m cli.main eval memory \
  --embeddings fixture --repetitions 20 --sizes 100 --save eval/results/my-size100.json
```

Functional tests and regression, using actual repository conventions (no `--no-db`
plugin; unset database variables instead):

```sh
HF_HUB_OFFLINE=1 venvmp/bin/python -m pytest -q
 env -u DATABASE_URL -u MEMORY_TEST_DATABASE_URL HF_HUB_OFFLINE=1 venvmp/bin/python -m pytest -q
venvmp/bin/python -m black --check api cli tests migrations mindpalace_sdk.py mcp_server.py examples/memory_demo.py examples/memory_evaluation_demo.py
venvmp/bin/python -m flake8 api cli tests migrations mindpalace_sdk.py mcp_server.py examples/memory_demo.py examples/memory_evaluation_demo.py
venvmp/bin/python -m compileall -q api cli tests migrations mindpalace_sdk.py mcp_server.py examples/memory_demo.py examples/memory_evaluation_demo.py
git diff --check
```

Generation is optional: configure the existing LLM provider explicitly and add
`--generation --embeddings cached`; source text may be sent to that provider and
cost money. It is not required by CI. Do not run downgrade commands against a
valuable memory database; destructive migration checks belong on a disposable DB.

## Conclusion and recommendation

The benchmark establishes that explicit state and provenance can survive evolving
sources, deletion, conflicting assertions and bounded packing consistently across
four interfaces. It does not establish general question understanding, generated
answer quality, broad contradiction reasoning, large-scale performance, security
readiness, or real customer adoption.

Memory Pack is useful as a portable auditable input **when lookup is controlled and
the budget is sufficient**. It is not yet a drop-in natural-language memory oracle.

M007 should prioritize bounded archive reads and measurable latency ceilings,
checkpointed/cancellable evaluation reports, retention/erasure and authorization,
then one actual developer/user workload with a local model. Address lexical-query
usability explicitly rather than hiding the 0/24 result behind tailored examples.
Do not claim M006's unmeasured generation and larger-scale acceptance checks are
complete merely because the deterministic tests pass.
