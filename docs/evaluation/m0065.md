## Service contract and implementation

The separate query operation is exposed as:

- REST **`POST /api/memory/query`**.
- SDK **`memory.query(query, ..., intent="auto")`**.
- MCP **`memory_query`**, with one `request` object.
- Remote CLI **`memory query --corpus ... --query ... --intent ...`**.

The question is mandatory/nonempty in the **`query` field**, not `question`, and
is limited to 2,000 characters. `intent` accepts **`auto` (default), `current`,
`historical`, `temporal`, `change`, `conflict`, `provenance`**. Supported selectors
are `path`, `as_of`, `valid_at`, `snapshot_id`, `budget`; query rejects `claim_id`
even if an adapter exposes it. Snapshot selection cannot be combined with
`as_of` or `valid_at`.

Existing lexical `current`, `history`, `changes`, `pack`, and other lookup
operations are unchanged. They still use lexical AND, not the new relevance
heuristic. Default `/api/query/ask` remains live RAG. Only explicit
`mode="memory"` maps its mandatory `question` to memory `query` with auto intent,
then optionally calls the configured LLM. That ask adapter exposes no intent
override; empty evidence short-circuits generation. The query endpoint itself
returns evidence-backed context, not generated prose.

### Time and intent are deliberately limited

Explicit `as_of`/`snapshot_id` selectors take precedence over dates/stages in the
question. Without them, a single `YYYY-MM-DD` is an inclusive observation cutoff
at **midnight UTC**, not end-of-day or authored validity. Invalid/multiple dates
are rejected. A recognized `stage A`-style phrase needs a caller-supplied real
`as_of` or `snapshot_id`; the service has no built-in stage calendar. Temporal
intent requires a parsed/explicit cutoff or snapshot. Snapshot replay fixes both
observation and validity; `valid_at` otherwise retains its separate authored
validity-window meaning.

Auto intent checks time selectors, conflict vocabulary, provenance, change,
current, then historical vocabulary, falling back to current. Explicit intent
wins over that inference. Relative phrases such as **“before Kafka” do not find a
precise before-entity event boundary**: they can select history, not synthesize an
event timestamp. Use captured selectors when a precise historical state matters.

### Relevance is not authority

The memory core first projects the complete time-scoped archive and resolves
current/history/uncertainty/conflicts. Ranking then embeds the question and each
archived claim's **claim text + authored key + path**. Normalized-vector dot
products are cosine similarities. Each authored key takes its maximum claim
score and is selected at:

```text
key_score >= max(0.30, 0.90 * top_key_score)
```

The **0.30 floor and 0.90 top-score band are heuristics**, not calibrated
confidence, truth, or authority. Historical vocabulary can find a key and thereby
its current assertion; propagation stays within the **same authored key**, not
an inferred equivalence class. It never promotes a historical claim to current.
Path filters constrain relevance, not authorization or conflict closure.
Connected conflict alternatives and all retained claims' evidence stay complete.

Current/temporal/conflict intent includes selected current claims and connected
conflicts (conflict is not a conflicts-only filter). Historical/change/provenance
also include historical and uncertain claims; historical/change include related
change events. Final selection is packed with the existing atomic evidence and
conflict budget rules.

The query service loads the **existing configured sentence-transformer on demand**,
reusing its in-process singleton if already initialized; other application
components can initialize it earlier. Inference is moved off the async event-loop
thread. **Question and claim vectors are recomputed for every query, transient,
with no persistent vector cache or index.** This does not embed archived files at
ingestion or rely on live chunk vectors that vanish on deletion. Lexical reads
do not need this model. Offline operation needs pre-cached weights; model
unavailability can return `503 memory_unavailable`.

Deterministic query selection requires the same archive state, observation and
validity clocks, question, intent, selectors, budget, **model and runtime**.
Snapshots freeze state/clocks, not embedding behavior across model/runtime
changes; independent wall-clock calls are not promised byte-identical.

## Measurements

### Strategy experiment (not three public query modes)

The experiment compares token-overlap lexical ranking, embedding ranking, and
hybrid reciprocal-rank fusion (constant 60), with authored-key propagation.
Token overlap here is **not** the old lexical AND operation that scored 0/24.
These are diagnostic strategies; the public query service uses embedding ranking.

| Strategy | Exact sets / 24 | Recall@1 | Recall@3 | Recall@5 | Recall@10 |
|---|---:|---:|---:|---:|---:|
| Token-overlap lexical | 15/24 | 68.75% | 83.33% | 95.83% | 100% |
| Embedding | 17/24 | 81.25% | 95.83% | 100% | 100% |
| Hybrid RRF | 9/24 | 72.92% | 87.50% | 100% | 100% |

High candidate recall does not mean the thresholded response is an exact set.
These small authored-scenario results are descriptive, not a statistically
established universal strategy advantage or broad held-out generalization test.

### Safety and budget correctness versus retrieval completeness

**0 safety failures across 264 output cases**: 64 main outputs plus 40 added
questions at each of five budgets (200 outputs). There were **0 execution
failures**. Checks cover exact archived provenance, complete canonical JSON
within budget, all-or-none conflict alternatives, no promotion to current
authority, and correct truncation relative to the full relevance-selected output.
Each of these five checks passed for all 264 outputs; this is not a claim about
all possible inputs or downstream LLM prompt-injection resistance.

| Budget (Unicode characters) | Added exact sets | Safety output cases passed |
|---|---:|---:|
| 1000 | 3/40 | 40/40 |
| 2000 | 3/40 | 40/40 |
| 4000 | 26/40 | 40/40 |
| 8000 | 30/40 | 40/40 |
| 16000 | 30/40 | 40/40 |

Measured retention across the 40 added questions (51 expected claim-text
occurrences; deduplicated within each answer including change/conflict context):

| Budget | Expected text retained | Unlabelled text retained | Truncated outputs | Maximum canonical characters |
|---|---:|---:|---:|---:|
| 1000 | 0/51 | 0 | 37/40 | 562 |

| 4000 | 44/51 | 7 | 13/40 | 3948 |
| 8000 | 45/51 | 11 | 0/40 | 5911 |
| 16000 | 45/51 | 11 | 0/40 | 5911 |

Unlabelled text is a deterministic proxy for irrelevant retention, not a human
judgment that every supporting context claim is irrelevant. Counts derive from
the saved per-budget responses; provenance remains complete even when retention
is zero. Larger budgets cannot repair a relevance-selection miss.

Budget correctness is **not retrieval completeness**. Whole claim/evidence or
conflict units may correctly be omitted when they do not fit. A correctly bounded
empty pack is not proof of absence, and `truncated=false` only says the selected
content fit, not that relevance found everything. Exact empty-set successes can
also be uninformative about nonempty-answer recall. The final artifact's
`passed: true` explicitly gates **safety and execution only**; it retains the
17 relevance failures rather than hiding them or changing their labels.

### Timings and live baseline

One fixed stage-G query (`question-restored-jwt-path-dispute`), path
`runbooks/auth-incident.md`, conflict intent, captured G cutoff, budget 8000:
**20 repetitions after an untimed warm-up**, with raw samples in the artifact.

| Measured boundary | p50 | p95 |
|---|---:|---:|
| Public query service (per-call embedding, archive projection, selection, pack) | **124.2 ms** | **131.3 ms** |
| Live hybrid+RRF search with query already embedded | **4.0 ms** | **5.1 ms** |

Query returned two claims/two evidence references/one conflict, 3821 canonical
characters, not truncated. Both measurements include session/savepoint overhead
but exclude workload setup and cold model loading. Query recomputes embeddings;
**the live search excludes query embedding**. Therefore this is **not a fair
end-to-end latency comparison**, not a speed ratio for complete user requests,
and not a distribution across questions, corpora, concurrency, or production
traffic. No new scaling result is established; full-history reads and per-query
embedding remain unbounded by the output budget.

The live baseline has no temporal/path selectors or claim-status authority model.
Its final-run literal expected-text availability is **20/25** original and
**38/51** added expected texts. These denominators count expected texts, not
questions; availability is not semantic accuracy, historical framing, or correct
conflict resolution. They are separate from M006's earlier coverage metric.

**Potential label issue, not a corrected label:**
`question-ownership-clarification` is a stage-B change query scoped to
`operations/ownership.md`, with `expected_historical_claims: []`. Stage B modifies
prose while preserving the authored owner claim (`memory_changed=false`,
`DOCUMENT_MODIFIED`). The core historical projection preserves assertions from
noncurrent versions, including semantically unchanged assertions. Returning that
prior-version claim is consistent with this core rule; the empty-history label
appears to conflict with it. This deserves label/contract review, not suppression
of history or silent relabeling. The failure and **30/40** score remain unchanged.

Other observed limits include related-concept contamination (transport versus
delivery, storage versus streaming), multi-part omissions, poor handling of
negated distractors and verbose temporal wording, and failure to abstain on an
unrelated payroll question. A temporal selector can choose the correct archive
state while relevance still picks the wrong keys. High recall@5 does not fix the
floor/band's actual omissions or extra selections. Authored-key propagation
helps old vocabulary find current assertions but cannot infer arbitrary semantic
relationships, source truth, or general contradictions.

already cached, use the local PostgreSQL instance on **port 5433** (substitute
your configured disposable database if different). It must permit isolated
schema creation and the migrations' extensions. No REST server or LLM is needed.
Run standalone, sequentially; database work uses the rollback-only sandbox.

substituting fixture vectors. The module requires `--save`, **overwrites an
existing target**, and does not create its parent. Use fresh filenames to preserve

module does not offer exclusive-create protection. An end-to-end safety/execution
failure exits nonzero; relevance misses alone do not. Neither command runs
generation. These are reproduction instructions, not a claim they were rerun
