ISOLATION
  Experiments run either inside a throwaway schema created in a transaction
  that is ROLLED BACK, or on a COMMITTED throwaway schema (named anx*) that the
  probe DROPS CASCADE before it exits. Every committed probe records
  schema_dropped_at_end / schema_dropped = true. Nothing in `public` was read
  for statistics or written. No index, migration, or DDL was created anywhere
  except inside these throwaway schemas.

  Where committed behaviour was the explicit subject (A2 split, A3, A4b, A4d,
  A5) a COMMITTED THROWAWAY SCHEMA was used, not a throwaway database.

==============================================================================
WHAT THIS MEANS FOR THE BENCHMARK ARCHITECTURE (A2 and A4 specifically)
==============================================================================

The benchmark architecture is SOUND on this axis, and the reason is stronger
than "ANALYZE rolls back".

1. Statistics are keyed by relation OID. Every harness run creates a NEW schema,
   so it gets NEW table OIDs, so nothing a previous run wrote can be visible to
   it. Measured in A4a: pass1 OIDs != pass2 OIDs, pass2 reltuples = -1,
   last_analyze = NULL, pg_statistic_rows = 0. Each run therefore genuinely
   starts from the fresh-install condition, and the "assert reltuples = -1"
   check in the old harness was asserting a real invariant, not a formality.

2. The prompt's stated danger -- "ANALYZE writes catalog rows that are NOT
   rolled back with the transaction" -- is real but only half of it. pg_class
   .reltuples and .relpages, plus the pg_stat_all_tables counters, DO survive a
   rollback. Only that matters if the TABLE survives the rollback. In the
   harness the table never survives, so it does not apply.

3. The dangerous shape needs COMMITTED DDL plus a rolled-back corpus: the
   relation lives on, reltuples describes rows that were never committed, and
   the planner believes it. That is measured in A4b/A4d. It did NOT degrade the
   plan at all -- because pg_statistic rolled back with the rows, the planner had
   a row count but no column statistics, and the index choice for this query is
   driven by index structure and the correlated-subquery shape, not by the row
   estimate. So even the genuinely hazardous case measured here is benign for
   this particular query.

4. The cliff itself is 100% explained by the ABSENCE of statistics:
   reltuples = -1 makes the planner choose idx_memory_claims_validity and
   filter, because with no row estimate it cannot know that (corpus_id,
   version_id) is the selective composite. A4a reproduces the bad plan at
   N=100 (12,194 blocks, Rows Removed by Filter = 99); A5 and Part C reproduce
   it at N=1000 (1,078,038 / 1,079,038 blocks, Rows Removed by Filter = 999).
   ANALYZE moves it to a true Index Cond on (corpus_id, version_id) at
   9,190 blocks.

5. Consequence for any proposed production hook: an ANALYZE placed INSIDE the
   write transaction would run once per document in the bulk path (sync_repo
   commits one transaction per document, ingestion.py:59 + 321-322), and if
   that transaction later rolls back it would leave reltuples describing
   abandoned rows (A2). Both are reasons to run it once, after commit, and not
   inside the write path. See 181-ingest-hook-analysis.txt.
