=== THE ANSWER ===

The tokenizer improvement does NOT generalize beyond held-out v1.

  v1 (used for diagnosis) : rescued 10, regressed 0 of 140
  v2 (blind, frozen)      : rescued 0, regressed 0 of 32

Lexical candidate recall is IDENTICAL in both arms on both datasets. The fix is
a genuine null on unseen questions. It neither helps nor hurts.

=== WHY -- this is the transferable finding ===

The fix works correctly. Tokenisation verified token by token:

  hv2-identifier-01  '...the 2024-11 incident'
     shipped   : [after constraint established incident the was which]  <- no digits
     candidate : [11 2024 after constraint ...]                         <- digits kept

The tokenizer defect is real and the candidate repairs it. But in v2 the
identifier questions were phrased with CONTENT WORDS that already reach the
claim ('constraint', 'deployment', 'release'), so the numeric token adds nothing
the lexical arm did not already have.

In v1 the rescued questions were the opposite shape:
  'Shipping 0.6 introduced what?'   tokens = [introduc, shipp]
  'What went wrong in 2024-03 ...'   tokens = [affect, order, went, wrong]

They contain NO content word from the gold claim. The identifier was the SOLE
bridge, which is exactly the case the tokenizer fix addresses.

CONCLUSION: the v1 result was real but non-generalising. It measured a property
of how v1 was WORDED, not a property of the retrieval system. The tokenizer
defect is genuine; its measured benefit was an artefact of question phrasing in
the set used to discover it. This is precisely why v2 existed.

=== DECISION ===

DO NOT SHIP the tokenizer fix. It is a null on unseen data and adds a parameter
plus a gate rule for no measured benefit. Per the shipping criterion, 'if v2
shows no improvement, revert/reject the tokenizer fix.'

It is recorded rather than erased: the tokenizer defect is real, and a future set
containing identifier-only questions would benefit. No such set exists outside
the one that produced the finding.
