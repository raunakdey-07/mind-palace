ITEM 1.6 -- EXPLAIN of the archive-load query, _load in api/services/memory.py
====================================================================================================

Server: PostgreSQL 15.19, shared_buffers=128MB, work_mem=4MB (session default), jit=on,
max_parallel_workers_per_gather=2, effective_cache_size=4GB. 8 cores.
Query: the exact statement from _load, narrow form (version_text=False, chunk_text=False),
which is what the public projection passes. Params path=NULL, as_of=NULL.
Corpus: m0117_scale.build_documents(n) + IngestionService(Offline embedder), throwaway
schema per size, rolled back after measurement. plan_cache_mode=force_custom_plan.
Runs: 3 per configuration, median reported. All three runs agreed closely at every size.

10,000-version result embeds tens of MB of jsonb. The evidence files keep the plan
structure and every timing/buffer/sort line verbatim, and collapse only that repeated
tuple payload with an explicit [ELIDED n Output: tuple lines] marker. The complete

5. THE PLAN-SHAPE CLIFF AT n=1000
----------------------------------------------------------------------------------------------------

The plan is IDENTICAL in shape at 2000, 3000, 5000 and 10000:
  Sort -> Nested Loop -> (memory_documents scan) x (memory_versions index scan),
  with three SubPlan aggregates, each on:
    chunks   memory_chunks_corpus_id_version_id_order_index_key
    claims   memory_claims_corpus_id_version_id_id_key
    evidence idx_memory_evidence_chunk
  and each carrying version_id in its Index Cond.

At n=1000 the plan is DIFFERENT. Two of the three aggregates switch to a
corpus-only index with no version_id:
    claims   idx_memory_claims_validity     Index Cond: (c_1.corpus_id = v.corpus_id)
    evidence idx_memory_evidence_claim      Index Cond: (e.corpus_id = v.corpus_id)

Buffer arithmetic, which is the isolation and not a guess:
  n=1000, evidence subplan: 1000 outer versions x 1008 blocks = 1,008,000 observed.
  n=1000, claims subplan:   1000 outer versions x   56 blocks =    56,000 observed.
  n=2000, both subplans:     2002 outer versions x    4 blocks =     8,008 observed.
  The scan walks the whole corpus once per outer row, so cost is O(versions x corpus).

Why the planner prefers it at 1000: it estimates rows=1 for both subplans and a
lower total cost (8.18 vs 8.43 for claims), so the corpus-wide index looks cheaper.
The estimate is wrong by the size of the corpus.

6. INTERPRETATION RULES
----------------------------------------------------------------------------------------------------

(a) EXPLAIN ANALYZE DOES NOT INCLUDE OUTPUT SERIALISATION OR TRANSFER TO THE CLIENT.
    It times the server producing tuples, not asyncpg receiving or decoding them.
    Therefore the wide-vs-narrow execution-time difference in section 1 is NOT the
    real byte-transfer saving and must not be read as one. The narrow projection
    only drops work the server was not doing anyway (it was not selecting those
    columns into the tuple in the first place); its real benefit is the transfer in
    section 4, which EXPLAIN cannot see. The projection, select and pack stages that
    DO pay the byte cost are measured by m0122_instrumented.py, not here.

(b) SORT METHOD AND SPILL AT EACH SIZE -- the key evidence:
    n=1000  quicksort,  1694 kB in memory, no temp blocks
    n=2000  quicksort,  3392 kB in memory, no temp blocks
    n=3000  external merge Disk,  617 temp blocks written
    n=5000  external merge Disk, 1030 temp blocks written
    n=10000 external merge Disk, 2060 temp blocks written
    The in-memory sort crosses work_mem=4MB between 2000 and 3000 versions.
    Note the control query also spills at 10000 (523 blocks) with no aggregates at
    all, so the ORDER BY itself is past work_mem before the aggregates are considered.

(c) IS THE PLAN IDENTICAL AT 1000 AND 5000? NO. The aggregate body is identical from
    2000 upward, including the join order, the version scan and all three subplan
    indexes. At 1000 two of the three subplans use a different, corpus-only index.
    1000 and 2000 are NOT the same shape, and neither is 1000 and 5000.
    Separately, the memory_documents access does change once at 3000, from an index
    scan to a bitmap heap scan on memory_documents_corpus_id_path_key. That is a small
    effect (644 -> 4050 buffers) and is not the cause of anything measured here.

(d) THE HYPOTHESIS 'the three jsonb_agg subqueries are the critical path' is
    SUPPORTED, with a qualification. Stripping the three aggregates and changing
    nothing else leaves 0.4% to 7.6% of the execution time at every size. But at
    n=1000 the aggregates are slow for a second, larger reason: the plan there is
    the pathological one in section 5. The aggregates are the critical path, and at
    1000 they are critical partly because the planner under-costs them.

(e) THE NON-MONOTONIC BEHAVIOUR IS ESTABLISHED, NOT GUESSED. Execution falls from
    566 ms at 1000 versions to 64.6 ms at 2000 versions -- 8.8x faster at double the
    data. The buffer count falls from 1,068,311 to 26,678 over the same step. The two
    are the same event and it is reproducible on a fresh schema. Whether the planner
    will make this choice for other corpora in production is NOT established here:
    every corpus in this run was built by the same generator, and the estimate
    error that drives the choice has not been traced to its source.

(f) work_mem=256MB changes the answer at 5000 and not at 1000. At 5000 it removes
    the spill entirely (external merge -> quicksort, 8554 kB) and cuts execution
    249.2 ms -> 167.5 ms, a 1.49x improvement, at identical buffer counts. At 1000
    it changes nothing (566.1 -> 570.9 ms, both quicksort, already no spill) -- the
    1000 cost is the index, not the sort. So spill and the index cliff are two
    separate effects and neither explains the other.

(g) NOT ESTABLISHED: the cause of the row mis-estimate that selects the corpus-only
    index at 1000. The whole query is estimated at rows=4 against 1000 actual; the
    memory_versions scan is estimated at rows=1 per document against ~3 actual. The
    corpus_id predicate is a bpchar equality on a 64-character hex value, and the
    statistics for it were not examined in this run. Naming the selectivity formula
    that produces rows=4 would be a guess and is not offered.
