## What 1.0.0 actually needs next

In the order that unblocks the most rows:

1. **Sealed scoring, once.** Rows 3, 4 and 5 all wait on it, and nothing else can
   substitute. It needs Hub access, or a model already in the local cache.
2. **A compatibility policy document.** Row 1 is one document long, and it is
   cheap. The contract test already enforces the line; the policy says what the
   line means.
3. **Re-run the lab against the product path.** Rows 4 and 8 are not fixable by
   writing; the measurement is wrong, and the fix is to measure the real path.
4. **Upgrade from `v0.8.0` with real data.** The schema path passes; the data
   path is blocked on `v0.8.0` having no `remember`. Either write the archive
   through `v0.8.0`'s actual ingestion surface, or record `v0.8.0` as
   unsupported with a stated reason.

## The two things a release must not claim

* **Sealed scoring has not happened.** Not once, on any set, ever. Held-out v1 is
  burned. Any release note implying otherwise is false.
* **A downgrade destroys tenant state.** 010 -> 007 drops `memory_principals` and
  disables row-level security on all 9 protected tables. Memory survives; the
  isolation model does not. This belongs in the upgrade notes for any 0.9.x
  release that carries 008-010, and it is not yet written down.
